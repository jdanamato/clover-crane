## Key Liquiflow Rules & Gotchas
 
- **Two liquid tags cannot be on the same element** — e.g. `li-for` and `li-if` cannot coexist on one element. Use the `:inside` modifier (`li-for:inside`, `li-if:inside`) or nest elements.
- **`li-object:text` and `li-object` are equivalent** — both set inner text content.
- **Bracket notation required for hyphenated handles** — `pages['about-us'].url` not `pages.about-us.url`.
- **`li-for:inside`** — renders the loop inside the element rather than wrapping it. Used on Swiper wrapper elements.
- **`li-settings` compatible modifiers**: `:text`, `:image`, `:url`, `:richtext`, `:number`, `:color`.
- **`li-form:product=""`** — empty value is intentional; tells Liquiflow to use the current page's product context.
- **`li-form:cart=""`** — same pattern for cart form.
- **`li-content-for-theme-blocks=""`** — empty value is correct; marks the block container for the section.
- **`cart.total_discounts`** — plural, not `cart.total_discount`.
- **`image_url` not `img_url`** — `img_url` is deprecated in Shopify. Use `image_url: width: [n]`.
- **`li-block` names must be unique within a section** — duplicate names cause schema conflicts.
- **`forloop.index` only works inside `li-for`** — never use it in a `li-block` context.
- **Properties starting with `_`** are hidden from customers by convention — filter them with `li-unless="property.first contains '_'"`.
- **Never wrap content in a `<template>` tag (e.g. Alpine `x-if`) in Webflow** — `<template>` content lives in an inert DOM fragment, not normal child nodes, and gets silently dropped on Webflow's code export. Every re-export reproduces the same empty `<template></template>`, even if the file is patched afterward. Use `x-show` on a plain element instead of `x-if`/`<template>` — same conditional-render behavior for this use case, survives export. (Found 2026-07-21 on `_sections/Product Hero.html`'s monogram picker — Style/Placement/Text/Color content kept vanishing on every export/publish cycle until switched from `<template x-if>` to `<div x-show>`.)
- **Any `x-data`/`x-bind:*`/`x-init`/etc. that needs to embed `{% %}` or `{{ }}` must be written as `li-attribute:<name>="..."`, not the bare Alpine attribute.** A bare `x-data="{ foo: { {% for %}...{% endfor %} } }"` looks like ordinary HTML and is easy to miss when auditing for raw-Liquid violations, but the Builder can't compile Liquid inside a plain attribute — the variable silently ends up `undefined`/empty at runtime with no build error, only a runtime Alpine console warning. (Found 2026-07-22 on `_sections/Product Hero.html` — a bare `x-data="{ ccSwatches: {% for %}... }"` for variant-swatch colors compiled to nothing, so every swatch fell back to its CSS default.)
- **`li-for` (bare) vs `li-for:inside`, concretely:** bare `li-for` on a flex/grid *container* div repeats the wrapper element itself once per item (each copy holds exactly one item), not just its children — breaks `flex-wrap` rows and CSS grids into a stack of single-item boxes even though the CSS itself is correct. Use `li-for:inside` whenever the loop should produce siblings inside one shared flex/grid wrapper.
- **The Liquiflow Builder can silently strip whitespace-only text nodes between tags when it re-serializes a `_sections/*.html` file on its own save cycle** (confirmed: a literal single space between two adjacent `<span>` tags disappeared from the *source file*, not just at Shopify publish). If you need inter-element spacing that must survive, use `&nbsp;` instead of a literal space character.
- **`product_option_value.swatch.color`/`.image` (Shopify's documented native option-swatch Liquid path) can return `nil` even when the option is correctly linked to a `shopify.color-pattern` metafield with real saved data** — confirmed on this project 2026-07-22, root cause unresolved (appears to be a Shopify-side platform issue, not a Liquiflow/theme bug). Working alternative: query the metaobject directly instead of relying on `.swatch` — `{% assign h = value.name | handleize %}{% assign entry = metaobjects['shopify--color-pattern'][h] %}`, then read `entry.color.value` / `entry.image.value`. Do not put a piped filter directly inside Liquid bracket notation (`metaobjects['type'][x | handleize]`) — assign the filtered value to its own variable first, then index with that plain variable.
- **Turning an element that already has `li-if` into a component (Builder's "create component" action) stacks `li-component` onto that same root node**, producing a `STANDALONE_CONFLICT` lint error (`li-if` + `li-component` on one element). This is Builder-generated, not a hand-authoring mistake — the component-creation flow doesn't split the conditional out automatically. A component's root element can't carry `li-if` itself. Fix: nest — wrap the component in an outer `<div li-if="...">`, keep `li-component` on the inner root only. Found 2026-07-23 on `_sections/Collections List.html`'s Pagination component (`li-if="paginate.pages > 1"` + `li-component="Pagination"` on the same div).
- **A `li-settings:custom` JSON embed must never contain a line break inside a JSON *string value* — the Builder's own re-serialization can put one there, and it silently deletes every setting in that embed.** The Builder pretty-prints `_sections/*.html` on its save cycle and hard-wraps long lines at the nearest whitespace — including whitespace *inside* a JSON string. `"label":"Half width"` came back as `"label":"Half\n                width"`, which is invalid JSON (raw control chars aren't legal in JSON strings). Liquiflow's converter then falls back to emitting **only the header** it derives from the attribute value, and drops the whole settings array — no build error, no lint warning, nothing in the Theme Editor. Confirmed 2026-07-30 against the published `Clover` theme on production: `_sections/Promoted.html`'s Panel block compiled to `"settings": [{"type":"header","content":"Panel"}]` while the block markup still referenced `block.settings.collection` / `.video` / `.half_width`, so the block showed up in the editor with zero fields. Defence: hand-format the embed as **one JSON object per line, short lines** so a re-wrap can only ever land between tokens, and validate with `JSON.parse` after any Builder save cycle:
  ```
  li-liquid>[
  {"type":"collection","id":"collection","label":"Collection"},
  {"type":"video","id":"video","label":"Video (optional, overrides image)"},
  {"type":"checkbox","id":"half_width","label":"Half width","default":false}
  ]
  ```
- **The value of `li-settings:custom` is only a Theme-Editor header label, not an id** (live docs, `section-settings/custom-settings`): `li-settings:custom="Panel"` produces `{"type":"header","content":"Panel"}` ahead of whatever JSON is inside the embed; leave the value empty for no header. That is exactly why the failure above is so quiet — a header-only schema is also the *correct* output for an empty embed, so a dropped array is indistinguishable from "no settings defined" in the compiled file.
- **`w-embed` is not required on a `li-settings:custom` element.** The live docs say to put the schema in a Webflow Embed, and `docs/project-reference.md` long quoted this project's embed as `class="hide w-embed"`, but no committed version of `_sections/Promoted.html` ever had `w-embed` on it — and the converter still recognised the attribute and stripped the element (verified 2026-07-30 on the compiled `sections/promoted.liquid`). Recognition is driven by the attribute, not the class.
- **Any `li-settings:custom` JSON embed needs `li-liquid` on the same element, or the setting silently fails.** *(Qualified 2026-07-30 — the causal claim below is unverified.* `li-liquid` was added to the Promoted embed on 2026-07-24 and the setting was reported fixed, but that was checked on staging, which is now deprecated as evidence; on production the Panel settings were still absent afterwards, explained by the JSON line-wrap bug above. `li-liquid` is documented only as "preserve the formatting of Liquid inside Custom Code elements" — it is not mentioned on the custom-settings page at all. Keeping it is harmless: the converter demonstrably still processed the attribute with `li-liquid` present. Treat "li-liquid fixes custom settings" as unproven, not as a rule.) Webflow's export mangles double quotes inside Custom Code/Embed elements (per `liquid-attributes/miscellaneous` docs) unless `li-liquid` is present to preserve formatting — without it, the JSON's quotes get corrupted, the schema fails to parse, and the Theme Editor setting just doesn't work, with no visible error anywhere. Found 2026-07-24 on `_sections/Promoted.html`'s Promoted Panel block — a `half_width` checkbox defined via `li-settings:custom` did nothing in the Theme Editor until `li-liquid` was added to the same embed div.
- **A section file can be stale/orphaned for reasons that have nothing to do with the current session — check before editing, every time, not just when something seems off.** `_sections/Hooper.html` was edited repeatedly across a whole session (including a Swiper.js migration) after it had *already* been renamed to `Stores` in the Builder (Webflow Designer side) *before that session even started* — confirmed via git status showing `_sections/Stores.html` as untracked-but-present, and `index.html` already referencing `li-section="Stores"`, from the very first message. Renaming in the Builder re-exports fresh from Webflow's canvas under the new name; it doesn't update or delete the old file, which just sits there looking normal and editable. All those edits to `Hooper.html` silently went nowhere. Found 2026-07-24. This was **not** a live/mid-session coordination problem the human needed to announce — it was a basic check the agent skipped: **before editing any `_sections/*.html` file, confirm it's still referenced by an actual page** (grep/read `index.html` or the relevant page file for its `li-section` value, or check `_liquiflow/session.json`'s `inventory.sections`). Do this once per file per session at minimum, not just when a rename is suspected — staleness can predate the session entirely. Renaming also leaves throwaway intermediate files matching partially-typed names (`Find .html`, `Find Your S.html`, `S.html` — each `li-section` a half-typed rename in progress); safe to delete once confirmed dead the same way.
